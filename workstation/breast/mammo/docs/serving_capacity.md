# 맘모 판독 서빙 실측

2026-09-07 · 소켓 4b · `infer_mammo.predict()` 서빙 경로 그대로

측정 스크립트 — `training/code/measure_latency.py` · `training/code/measure_capacity.py`
대상 — CBIS 테스트 40장 (앞 2장은 준비 구간이라 버림)

---

## 1. 왜 쟀나

소켓 타임아웃 값이 미정이었다. 짐작으로 정하면 둘 중 하나가 된다.

- 너무 짧으면 멀쩡한 판독이 끊긴다
- 너무 길면 죽은 요청이 앞을 막는다

평가 스크립트가 아니라 `serve_mammo.py:166` 과 같은 형태로 불렀다.
`predict(bundle, <바이트>, name=...)` — 소켓이 실제로 무는 구간이다.

---

## 2. 두 번 쟀고, 값이 두 배 차이났다

GPU 를 다른 팀과 공유한다. 두 측정 사이에 그쪽 사용량이 13GB 에서 21GB 로 늘었다.
같은 사진 40장이다.

| | 다른 팀 13GB | 다른 팀 21GB |
|---|---|---|
| 중앙 | 5.63초 | 약 9.6초 |
| 95퍼 | 12.24초 | **26.9초** |
| 최대 | 14.20초 | **28.5초** |
| 검사 1건(사진 4장) 95퍼 | 49.0초 | **107.6초** |

> **모든 설정값은 오른쪽 열을 기준으로 한다.**
> 한가할 때 잰 값으로 타임아웃을 정하면 바쁠 때 전부 끊긴다.

부수 값

- 모델 적재 20.2초 — 서버가 뜰 때 한 번. 요청마다 드는 것이 아니다
- 파일 읽기 0.016초 — 무시 가능

## 3. 느려지는 원인이 둘이고, 성질이 다르다

### 병변 수 — 예측 가능, 상한 있음

서술어 모델은 병변 하나마다 조각을 오려 돌린다. 그래서 병변이 많으면 오래 걸린다.

| 병변 수 | 사진 | 중앙 |
|---|---|---|
| 1~2개 | 5 | 8.19초 |
| 3~5개 | 23 | 9.56초 |
| 6~10개 | 9 | 10.96초 |
| 11개 이상 | 3 | 19.24초 |

바탕 시간 7.73초 + 병변당 0.88초.
실제 최대 21개 → 예상 26.1초, 실측 최대 28.5초.

**상한이 있다.** 병변 수는 검출 단계에서 정해지므로, 요청을 받은 뒤 대략 예측할 수 있다.

### GPU 경합 — 예측 불가, 상한 없음

최댓값은 병변 수를 따라가지 않는다. 병변 1~2개짜리가 19.66초 걸린 사진이 있고,
3~5개짜리의 최대는 18.11초다. 병변이 적은 쪽이 더 오래 걸렸다.

**중앙값이 올라가는 것은 병변 수, 최댓값이 튀는 것은 경합이다.**

### 이것이 뜻하는 것

같은 사진을 다시 넣어도 병변 수는 그대로다. **재시도로 못 넘긴다.**
타임아웃을 짧게 잡으면 병변이 많은 사진만 골라서 죽는데, 그것이 정확히
놓치면 안 되는 사진이다.

## 4. 워커는 1개다

| | |
|---|---|
| 최고점 실제 필요량 | 10,641MB |
| 최고점 할당자 점유 | 10,762MB |
| 적재 직후 점유 | 6,895MB |

적재 시점 6.9GB 에서 추론 중 10.6GB 까지 오른다. 타일 배치와 병변별 조각 때문이다.

최고점에서 캐시는 121MB 뿐이다. **10.6GB 는 실제로 필요한 양이고 줄일 수 없다.**
측정 종료 후 3.5GB 가 반납되지만, 워커가 둘이면 둘 다 최고점을 찍으므로
그 반납분은 계산에 넣을 수 없다.

```
카드 전체        32,607MB
− 다른 팀        21,217MB
− 판독 워커 1개  10,641MB
= 남는 것           749MB
```

### 이것은 용량 문제가 아니라 안정성 문제다

749MB 는 「워커를 더 못 띄운다」가 아니라 **「지금 OOM 에서 749MB 떨어져 있다」**는
뜻이다. 다른 팀이 배치를 조금만 키우면 판독이 죽는다.

### 조건이 둘이고, 숫자가 다르다

| | 카드 공유 (측정 조건) | 카드 단독 (시연 조건) |
|---|---|---|
| 쓸 수 있는 메모리 | 11.4GB | 32.6GB |
| 워커 | 1개 | 2~3개 |
| OOM 여유 | 749MB | 21.9GB |
| 사진 1장 95퍼 | 26.9초 | 12초 안팎 |
| 검사 1건 95퍼 | 107.6초 | 50초 안팎 |

**시연은 단독 조건으로 한다.** 그 조건에서는 749MB 문제가 없다.

> 다만 「시연 때 다른 팀이 안 쓴다」가 **합의**인지 **예상**인지 확인할 것.
> 예상이라면 당일에 누가 학습을 걸어두는 순간 위 표의 왼쪽 열이 된다.

설정값(6절)은 **왼쪽 열 기준으로 정한다.** 근거는 6절 끝에.

## 5. 그래서 판독 API 는 동기로 만들 수 없다

워커 1개이므로 요청이 겹치면 줄을 선다. 기다리는 시간은 추론 시간이 아니라
**앞에 밀린 것 + 내 것**이다.

검사 3건이 동시에 오면 세 번째는 시작도 못 한 채 약 430초를 기다린다.
HTTP 연결을 그만큼 붙들면 게이트웨이 기본 타임아웃(보통 30~60초)에 먼저 잘린다.
우리가 정한 값과 무관하게 잘린다.

```
POST /mammo/read        → 202 + job_id      즉시 반환
GET  /mammo/read/{id}   → 진행 상태 또는 결과
```

DB 스키마 v9 의 `ai_result.run_status` 가 이미 `queued · running · done · failed` 다.
스키마는 맞는 방향으로 가 있다.

## 6. 타임아웃 — 세 겹으로 나눈다

| 겹 | 값 | 근거 | 넘으면 |
|---|---|---|---|
| ① 워커가 사진 1장에 무는 시간 | **54초** | 95퍼 26.9초 × 2 | 그 사진만 버리고 다음으로 |
| ② 작업 1건(검사 4장) | **216초** | ① × 4 | 작업을 실패로 적고 큐에서 뺀다 |
| ③ 클라이언트 대기 | **두지 않는다** | 202 즉시 반환 | — |

③ 대신 **큐 깊이에 상한**을 두고 넘치면 503 으로 거절한다.
무한정 쌓이면 뒤에 온 요청이 ②를 넘겨 전부 실패한다.

95퍼에 2배를 두는 이유는 경합이다. 다른 팀 사용량이 13GB → 21GB 로 바뀌었을 때
값이 두 배가 됐다. 그 위에 21GB 보다 더 쓰는 경우가 남아 있다.

### 시연 때 GPU 가 한가해도 이 값을 내리지 않는다

한가하면 요청이 12초에 끝난다. 54초 타임아웃은 **한 번도 안 터진다.**
넉넉한 타임아웃은 한가할 때 대가가 없다 — 느린 요청이 있을 때만 작동한다.

반대로 24초로 좁히면 시연은 잘 돌지만, 카드를 나눠 쓰는 환경에서
**병변이 많은 사진만 골라서 죽는다.** 그것이 놓치면 안 되는 사진이다.

코드는 제출물이므로 보수적인 값으로 간다.

## 7. 팀에 요청할 것

### DB — `ai_result` 에 한 칸

```
requested_at   timestamptz    요청이 큐에 들어온 시각
```

지금은 `analyzed_at`(끝난 시각)과 `elapsed_sec`(추론 시간)만 있다.
「90초 걸렸다」가 큐에서 78초 기다린 것인지 추론이 90초 걸린 것인지 구분되지 않는다.
이 둘은 고치는 방법이 정반대다 — 앞은 워커를 늘리거나 거절해야 하고,
뒤는 모델을 손봐야 한다.

`대기 = analyzed_at − elapsed_sec − requested_at`

### 운영 — GPU

발표 시연 시간대 GPU 단독 사용 **합의**. 근거는 4절.
그 조건에서는 판독이 두 배 빠르고 OOM 여유가 21.9GB 다.
합의가 아니라 예상 상태로 두면 당일에 뒤집힌다.

### 팀이 정해야 하는 값 (측정으로 안 나온다)

**큐 깊이 상한.** 깊이 D 일 때 최악 대기는 `(D+1) × 216초` 다.

| 깊이 | 최악 대기 |
|---|---|
| 1 | 7.2분 |
| 2 | 10.8분 |
| 3 | 14.4분 |

「판독 결과를 몇 분까지 기다려도 되나」를 정해야 깊이가 나온다.
이건 임상 쪽 판단이다.

## 8. 이 숫자들의 유효 범위

- **다른 팀 사용량 21GB 기준이다.** 그 값이 바뀌면 결론도 바뀐다
- 발표 자료에는 「카드를 공유하는 조건에서 워커 1개」로 적는다
- 병변 수 관계는 CBIS 테스트 40장에서 나왔다. 병변 11개 이상은 3장뿐이라
  그 구간의 중앙값 19.24초는 표본이 얇다
- 워커 2개 실측은 하지 않았다. 다른 팀이 GPU 를 쓰는 중에 10.6GB 를 더 잡으려다
  실패하면 그쪽 학습이 같이 죽는다. 필요를 확인한 뒤 그쪽과 합의하고 잰다
