환자 앱 화면 명세
2026-09-09 갱신 · DB 스키마 v10 기준
---

> **이 문서는 「화면마다 무엇을 하나」다.** 세부는 셋으로 나뉘어 있다.
>
> | 무엇 | 어디 |
> |---|---|
> | 화면 생김새 · 설계 규칙 | 목업 아티팩트 |
> | 화면 순서 · 알림 딥링크 | 흐름도 아티팩트 |
> | **API · 응답 화이트리스트 · 문구집** | **「환자 앱 구현 계약」 아티팩트** |
>
> 넷이 어긋나면 **계약 문서가 원본**이다. 응답 필드와 화면 문구는 거기서만
> 고친다.


> 화면 순서는 **사용 흐름대로** 다시 매겼다. 원래 목록과의 대응은 이렇다.
> `1 로그인` `2 등록 확인(=회원가입)` `3 문진` `4 예약` `5 검진 결과`
> `6 처방` `7 챗봇`

## 먼저 — 구조에서 나오는 제약 넷

화면을 짜기 전에 이것부터 정해야 한다. 넷 다 「그렇게 만들면 안 되는」 것들이다.

**① 가입은 «신규 등록» 이 아니라 «본인 연결» 이다.**
`patient.account_id` 가 null 인 것이 「원무가 등록했지만 앱 미가입」이다.
가입할 때 본인확인으로 그 행을 찾아 계정에 붙인다.

```
원무가 patient 생성 (account_id = null)  ← 내원 시
  → 환자가 앱에서 가입 · 본인확인
  → 등록된 행과 대조해 연결
  → 그 순간부터 과거 검사 · 승인된 안내문 · 예약이 보인다
```

**가입의 값어치가 여기 있다.** 계정을 만드는 것이 목적이 아니라
**과거 기록에 접근하는 열쇠**를 만드는 것이다. 화면 문구도 그렇게 간다.

**② 앱은 검사 오더를 만들지도, 예약을 잡지도 않는다.**
`exam_order.exam_purpose` 가 NOT NULL 이고 값이 `screening · diagnostic` 이다.
**검사 목적은 의료진이 정하는 것**이고, 확정 사양서에서 「오더 생성 시 목적이
비어 있으면 저장 불가」로 게이트를 걸어 뒀다. `ordered_by` 도 FK staff 다.

**예약도 병원에서 잡는다**(09-07 확정). 그래서 예약 화면은 쓰기가 없는
**조회 화면**이다. 「검사 예약하기」가 아니라 **「내 검사 일정」** 이다.
일정을 바꾸려면 병원에 연락해야 하므로 그 경로를 화면에 둬야 한다.

**③ 앱에 뜨는 결과는 «환자용으로 따로 쓴 안내문» 이다.**

판독 소견서를 그대로 보여주는 것이 아니라, **의사가 환자가 읽을 수 있게
정제해서 쓴 문서**만 앱에 간다.

```
report.audience = 'patient'        환자용으로 작성된 문서
report.lock_status = 'unlocked'    설명을 마치고 의사가 승인한 것
```

**앱은 이 둘을 동시에 만족하는 것만 읽는다.** 그래서 앱 입장에서
「잠긴 결과」라는 상태는 존재하지 않는다 — 승인 안 된 문서는 아예 안 보인다.

**④ 그래서 앱은 등급·수치를 «따로» 표시하지 않는다.**

문서에 등급을 넣을지 말지, 어떤 말로 쓸지는 **의사가 그 문서를 쓰면서
정한다.** 앱이 `assessment.category` 를 DB 에서 따로 꺼내 화면에 붙이면
**문서와 어긋날 수 있다** — 의사는 「추적 관찰이 필요합니다」라고 썼는데
앱이 옆에 「4a」를 띄우는 식이다.

```
보여준다   의사가 쓴 문서 본문 · PDF
안 한다    assessment.category · lesion.birads_model · malignancy_p
           병변 위치 그림 · AI 판단 일체
```

경로를 하나로 유지하는 것이 핵심이다.

## 1. 로그인

**읽고 쓰는 곳** `account` (login_id · password_hash · role · is_active ·
push_token · last_login_at)

| | 기능 |
|---|---|
| 필수 | 아이디·비밀번호 로그인 · 토큰 저장 · 자동 로그인 |
| 필수 | 로그인 직후 `push_token` 등록 |
| 필수 | 로그아웃 (토큰 폐기 + push_token 비우기) |
| 필수 | 토큰 만료 시 조용히 갱신 · 실패하면 로그인 화면으로 |
| 필요 | 비밀번호 재설정 (전화 인증 경유) |

**막히는 것** — `account` 가 환자·의료진 공통이다. `role='patient'` 가
아닌 계정으로 앱에 로그인하려 하면 **서버가 막아야 하고, 앱도 응답의
role 을 확인해서 거부해야 한다.** 둘 다 하는 게 맞다.

`is_active=false` 와 `phone_verified=false` 는 각각 다른 안내가 필요하다
(정지된 계정 / 본인확인 미완료).

## 2. 회원가입

**읽고 쓰는 곳** `patient` · `patient_pii` 대조 → `account` 생성 →
`patient.account_id` 연결

가입에 성공하면 **그 환자의 검사 이력 · 승인된 안내문 · 예약이 보인다.**
그래서 본인확인이 이 화면의 전부다.

| | 기능 |
|---|---|
| 필수 | 본인확인 — 이름 · 생년월일 · 휴대폰 |
| 필수 | SMS 인증 (재발송 타이머 · 시도 횟수 제한) |
| 필수 | 아이디 · 비밀번호 설정 (규칙 안내 + 중복 확인) |
| 필수 | 약관 · 개인정보 처리 동의 |
| 필요 | 병원 등록번호 입력 (있으면 대조가 확실해진다 · 선택) |

### 주민번호는 받지 말자 — 안 받아도 동명이인이 걸러진다

주민번호를 쓰려는 이유가 동명이인 구분이라면, **이미 해결돼 있다.**

```
patient_pii.phone   UK (null 제외)   ← 전화번호 자체가 유일하다
```

**이름 + 생년월일 + 그 번호로 SMS 를 받는 것**, 셋이 동시에 맞을 확률은
사실상 0 이다. 그리고 휴대폰 인증은 「그 번호를 지금 쥐고 있는 사람」을
확인하는 것이라 **주민번호보다 실질적인 본인확인**이다.

반면 주민번호를 받으면 부담이 생긴다.

| | 내용 |
|---|---|
| 법 | 개인정보보호법 제24조의2 — **법령에 구체적 근거가 있어야** 처리 가능. 앱 본인확인은 그 근거가 아니다 |
| 의무 | 받는 순간 암호화 · 분리보관 · 접근통제 의무가 붙는다 |
| 위험 | 유출 시 파장이 다른 정보와 비교가 안 된다 |
| 실익 | **없다.** 앞 7자리는 `birth_date` + `sex` 와 같은 정보이고 둘 다 v8 에 이미 있다 |

**v8 `patient_pii` 에도 주민번호 칸이 없다**(name · birth_date · phone).
v5 부터 「주소·주민번호는 없음」으로 정해 둔 것이다. 그대로 가는 게 맞다.

### 실패 경로를 셋으로 나눈다

```
대조되는 환자가 없다   → 병원 방문 이력을 확인해 주세요 (안내 + 전화)
정보가 안 맞는다        → 입력을 다시 확인해 주세요
이미 가입돼 있다        → 로그인하거나 비밀번호를 찾으세요
```

⚠ 너무 자세히 구분하면 남의 정보를 넣어 **가입 여부를 알아낼 수 있다.**
시도 횟수 제한을 반드시 건다.

### 방문 이력이 있는 사람만 가입된다  *(2026-09-07 확정)*

대조되는 `patient` 행이 없으면 가입을 막고 안내만 한다. 앱이 `patient`
행을 만들지 않는다.

`patient_number` 가 UK NOT NULL 이라 앱이 환자를 만들려면 임시값이
필요하고, 첫 내원 때 원무가 실제 번호로 바꾸는 이관 절차가 없으면
미연결 계정이 쌓인다. **검진 CDSS 라 환자는 병원에 온 뒤 앱을 쓰므로
막아도 잃는 것이 없다.**

## 3. 문진

**읽고 쓰는 곳** `patient.questionnaire` JSONB · `patient.has_allergy` ·
`patient.allergy_note`

```
questionnaire = {has_symptom, family_history, past_history,
                 menopause_status, risk_model, risk_lifetime_percent,
                 risk_tier, answered_at}
```

| | 기능 |
|---|---|
| 필수 | 문항 폼 (분기 있음 — 증상 있으면 추가 질문) |
| 필수 | **알레르기 문항** — 조영제 알레르기는 검사 진행 차단 사유다 |
| 필수 | 임시 저장 · 이어서 작성 |
| 필수 | 제출 후 요약 보기 |
| 필요 | 위험도 결과 표시 (`risk_tier` · `risk_lifetime_percent`) |

**앱이 위험도를 계산하면 안 된다.** `risk_model` · `risk_lifetime_percent` ·
`risk_tier` 는 서버가 계산해 넣는 값이다. 앱은 표시만 한다.

**막히는 것** — `questionnaire` 는 **최신 1건만** 저장된다(JSONB 한 칸).
「지난 문진 보기」를 만들 수 없다. 화면에서 그 기능을 약속하면 안 된다.

## 4. 예약 — **보기 전용 달력**  *(2026-09-07 확정)*

**예약은 병원에서 잡는다. 앱은 잡힌 일정을 보여주기만 한다.**
쓰기가 없으므로 이 화면은 조회 화면이다.

**읽는 곳** `exam_order` (scheduled_at · order_status · modality ·
exam_purpose · visited_at) · `followup.due_at`

### 달력에 무엇을 띄우나

```
확정된 검사     exam_order.scheduled_at 이 있는 것        ● 점 표시
추적 예정       followup.due_at (오더는 아직 없다)        ○ 다른 표시
```

둘을 **같은 모양으로 그리면 안 된다.** 앞은 잡힌 일정이고 뒤는
「이맘때 오셔야 합니다」라는 안내다.

### 검사 상태 표시 — `order_status` + `visited_at` 조합

```
ordered  · scheduled_at 없음   일정 조율 중 — 병원에서 연락드립니다
ordered  · scheduled_at 있음   예정
accepted                       확정
in_progress                    진행 중
completed · visited_at 있음    완료
completed · visited_at 없음    미내원
cancelled                      취소됨
```

| | 기능 |
|---|---|
| 필수 | 월 단위 표 달력 (스크롤 아님) · 이전/다음 달 |
| 필수 | 날짜 탭 → 그날 검사 상세 |
| 필수 | 검사 목록 — 예정 · 지난 것 |
| 필수 | **병원 전화 걸기 버튼** — 아래 |
| 필수 | 알림 — 예약 잡힘 · 변경됨 · 하루 전 · 당일 |
| 필요 | 추적 예정일 표시 (`followup.due_at`) |
| 필요 | 검사별 준비사항 안내 — 정적 콘텐츠, DB 불필요 |

**전화 걸기 버튼이 실제로 중요하다.** 앱에서 예약을 못 바꾸므로 환자가
일정을 바꾸려면 병원에 연락하는 수밖에 없다. 그 경로가 화면에 없으면
사용자가 막힌다. 「예약을 변경하시려면 병원으로 연락해 주세요」 +
전화 버튼을 검사 상세에 둔다.

**준비사항은 모달리티마다 다르다.** 맘모는 데오도란트·파우더 금지,
MRI 는 금속 제거와 조영제 알레르기 확인이 있다. `modality` 로 갈라
정적 문구를 띄우면 되고 DB 는 필요 없다.

## 5. 검진 결과 — 환자용 안내문 열람

**읽는 곳** `report` 중 `audience='patient'` **AND** `lock_status='unlocked'`
(본문 `narrative_text` · `content_json` · PDF `pdf_object_key`)

### 화면 상태는 둘이다

```
안내문 있음     본문 + PDF
안내문 없음     "결과 안내는 병원 방문 시 받으실 수 있습니다"
```

앞 판에서 상태를 넷으로 잡았는데 **설계가 바뀌어 둘로 줄었다.**
「판독 중」과 「잠김」이 앱에서는 구분되지 않는다 — 둘 다 「아직 안내문이
없다」로 같다.

⚠ **검사 이력은 보이는데 안내문만 없는 상태가 정상이다.** 환자가
「검사는 받았는데 결과가 없다」고 느끼지 않게 문구를 써야 한다.
「결과가 없습니다」가 아니라 **「병원 방문 시 안내받으실 수 있습니다」** 다.

| | 기능 |
|---|---|
| 필수 | 안내문 본문 |
| 필수 | PDF 보기 · 저장 |
| 필수 | 열람 기록 — 서버가 `last_viewed_at` · `view_count` 갱신 |
| 필수 | 모르는 말 → **챗봇으로 넘기기** (7절) |
| 필요 | 다음 일정 안내 (`followup.due_at` · 예정 검사) |
| 필수 | **최종 판단은 의료진** 고지 |

### 과거 기록

계정이 연결되면 그 환자의 이력 전체가 보인다.

| | 내용 |
|---|---|
| 검사 이력 | `study` · `exam_order` — 날짜 · 종류 · 상태 |
| 안내문 이력 | 승인된 환자용 `report` 만 |
| 추적 이력 | `followup` 회차 · 다음 예정일 |

```
2026-03-14  맘모그래피   안내문 보기
2025-09-02  맘모그래피   병원 방문 시 안내
2025-03-11  유방초음파   안내문 보기
```

**등급 변화 그래프 같은 것은 만들지 않는다.** 등급을 앱이 직접 다루지
않기로 했으므로(제약 ④), 이력도 안내문 유무로만 표시한다.

### 안내문은 어떻게 만들어지나 — 웹 쪽에서 확정됨

```
판독 소견  →  AI 생성 (환자 열람 제약을 프롬프트에 넣어 정제)
           →  의사 검토 · 수정
           →  의사 승인  →  lock_status = unlocked  →  앱에 뜬다
```

**앱은 누가 썼는지 신경 쓰지 않는다.** `audience='patient'` 이고
`unlocked` 면 의사가 책임지고 승인한 문서다. 그래서 앱 쪽 작업은
이 설계와 무관하게 진행할 수 있다. (작성 화면은 의료진 웹 담당)

### ★ 그런데 API 규칙이 하나 생긴다 — `report` 행을 통째로 내리면 안 된다

`report` 에는 **환자가 보면 안 되는 내부 필드가 섞여 있다.**

```
내려도 됨   narrative_text · pdf_object_key · explained_at
            (+ study 에서 검사 날짜 · 종류)

내리면 안 됨  dropped_sentences   제약에 걸려 «잘려 나간 문장» 이다.
                                 환자가 보면 안 되는 내용이 그대로 들어 있다
              fallback           AI 생성이 실패해 대체 문구를 쓴 것.
                                 「AI가 못 썼다」를 환자가 알 이유가 없다
              prompt_version     내부 값
              evidence_links     내부 참조 (lesion · assessment 를 가리킨다)
              unlocked_by · unlock_reason · issued_by · explained_by · socket_id
              content_json       무엇이 들었는지 확인 필요 — 그전엔 안 내린다
```

**`dropped_sentences` 가 제일 위험하다.** 이름 그대로 **정제 과정에서
걸러낸 문장**이라, 그걸 같이 내려보내면 **제약을 건 의미가 사라진다.**
DRF 시리얼라이저를 화이트리스트로 짠다 — 「빼야 할 것」을 나열하는 방식은
필드가 늘 때 새는 쪽으로 실패한다.

## 6. 처방 정보 — **지금은 만들 수 없다**

`prescription` 계열 테이블이 **v6 에서 MVP 밖으로 빠졌고 v8 에 없다.**
처방 내용을 담을 데가 아무 데도 없다.

시간이 남아서 만들기로 하면 **테이블부터 필요하다** — 처방 헤더 1행 +
약 여러 줄이라 최소 2개. 화면 작업은 그다음이다.

지금 할 수 있는 것은 **자리만 잡아 두는 것**(메뉴에 두고 「준비 중」)이다.

## 7. 챗봇 — 용어 풀이 · 관리 방법 안내

**목적** 결과지나 처방에 나오는 **말이 어려울 때 풀어 주는 것**, 그리고
**일상 관리 방법**을 알려 주는 것. 결과를 대신 조회해 주는 것이 아니다.

**저장 안 함** — 세션 캐시만. DB 테이블 없음 (v6 결정). Go → Ollama.

### 다루는 것과 안 다루는 것

```
다룬다   BI-RADS 4a 가 무슨 뜻인가 · 조직검사는 어떻게 하나
         맘모그래피 전 준비물 · 검사가 아픈가 · 얼마나 걸리나
         약 이름을 입력하면 무슨 약인지 · 복용 시 주의
         추적검사는 왜 6개월인가 · 유방 자가검진 방법

안 한다   내 결과 조회 («내 등급 알려줘» → 결과 화면으로 보낸다)
         개인 판단 («당신은 괜찮습니다» · «걱정 안 해도 됩니다»)
         진단 · 처방 · 복약 변경 지시
```

| | 기능 |
|---|---|
| 필수 | 대화 UI · 스트리밍 표시 · 중단 버튼 |
| 필수 | 세션 캐시 (TTL) · 앱 재시작하면 초기화 |
| 필수 | 응답 실패 · 지연 안내 (Ollama 가 안 떠 있을 수 있다) |
| 필수 | **면책 문구 상시 노출** |
| 필수 | 자주 묻는 질문 버튼 — 빈 입력창은 아무도 안 쓴다 |
| 필수 | **결과 화면에서 넘어오는 경로** — 안내문 읽다가 바로 묻게 |
| 필수 | 응급 신호 감지 → 병원 연락 안내 |

### 환자용 규칙 — 프롬프트에 박을 것 넷

**① 챗봇은 환자 데이터에 접근하지 않는다.**
DB 를 안 읽는 구성으로 간다. 「용어를 풀어 주는 것」이 목적이면 환자
데이터가 필요 없다. 안 읽으면 잠금 우회도 원천적으로 불가능하다.

**② 일반 설명과 개인 판단의 경계를 긋는다.**
여기가 제일 미끄러지기 쉽다.

```
좋다   "4a 는 악성 가능성이 낮지만 조직검사를 권하는 등급입니다"
나쁘다  "4a 시면 크게 걱정 안 하셔도 됩니다"
```

앞은 용어 설명이고 뒤는 **환자 한 사람에 대한 의학적 판단**이다.
환자가 자기 등급을 말해 줬더라도 뒤쪽으로 넘어가면 안 된다.

**③ 응급은 안심시키지 말고 병원으로 보낸다.**
「멍울이 만져져요」 「피가 나와요」 같은 입력에 챗봇이 괜찮다고 하면 안 된다.
**바로 병원 연락 안내로 전환**한다.

**④ 면책 문구는 판독 쪽과 같은 것을 쓴다.**
맘모 서빙 응답에 `disclaimer` 필드가 이미 있다. 시스템 안에서 문구가
갈리면 안 된다.

### 로그 정책 — 여기가 실제 위험이다

DB 에 안 넣기로 한 근거가 「익명 로그」인데, **환자가 자기 결과지를
대화창에 붙여넣으면 그 순간 로그가 개인정보가 된다.** 「4a 가 뭐예요」를
물으려면 결과를 보고 치는 것이 자연스러우니 실제로 자주 일어난다.

**확정 (2026-09-07) — 대화 내용을 남기지 않는다.**

```
남긴다   질문 수 · 응답 시간 · 실패율 · 모델 판   ← 운영 지표만
안 남긴다 사용자 입력 · 모델 출력 전문
```

챗봇 품질 개선용 로그가 필요해지면 그때 동의를 따로 받는 것이 맞지,
기본값으로 쌓아 두면 안 된다.

### 약제 안내는 처방 화면 없이도 된다

처방 테이블이 없어 6절 화면은 못 만들지만, **환자가 약 이름을 직접 입력**
하는 방식이면 챗봇은 지금 만들 수 있다. 처방 화면이 생기면 그때 「이 약에
대해 물어보기」 버튼으로 이으면 된다.

## 8. 알림함  *(09-08 추가)*

**읽는 곳** `notification`

푸시를 껐거나 잠금화면에서 지나친 사람을 위한 자리다. **알림이 사라지면
「연락 안 왔다」가 된다.**

| | 기능 |
|---|---|
| 필수 | 목록 · 읽음 표시 (`acknowledged_at`) |
| 필수 | 누르면 해당 화면으로 (딥링크) |

```
report_ready          → 안내문 본문
reservation_created   → 검사 일정 (해당 날짜)
reservation_changed   → 검사 일정 (해당 날짜)
followup              → 검사 일정 (추적 예정)
discordance           → **앱에 안 띄운다** — 의료진 알림이다
```

**다섯 종류 중 넷만 환자에게 간다.** 종류를 전부 받아서 그리면 마지막 줄이
새어 나간다.

## 9. 내 정보 · 동의  *(09-08 추가)*

**읽고 쓰는 곳** `account` · `consent`

`consent` 에 `withdrawn_at` 이 있다 — **철회할 수 있다는 뜻**이고,
그러려면 화면에 그 경로가 있어야 한다.

| | 기능 |
|---|---|
| 필수 | 동의 내역 — 문서 · 판 · 날짜 · **경로** |
| 필수 | 철회 (서버가 정한 것만) |
| 필수 | 알림 설정 (종류별 on/off) |
| 필수 | 로그아웃 |

**경로(`channel`)를 화면에 반영한다.** `app · paper · counter` 인데,
원무 창구에서 종이로 받은 동의도 같은 표에 들어온다.
**앱에서 받은 것처럼 보이면 안 된다** — 「창구에서 동의하셨습니다」로 적는다.

**철회 가능 여부는 서버가 내려준다.** 앱이 `doc_type` 을 보고 「필수니까
철회 불가」로 판단하면 **약관 판이 늘 때마다 앱을 다시 배포해야 한다.**
응답의 `withdrawable` 을 그대로 따른다.

가입 때 `doc_sha256`(그 판 본문의 해시)을 함께 보낸다. 판 번호만으로는
나중에 약관 파일이 바뀌었을 때 무엇에 동의했는지 증명이 안 된다.

## 화면마다 네 상태를 그린다  *(09-08 추가)*

위의 화면 설명은 전부 **잘 되는 경우**다. 실제 사용의 상당 부분이 아래 넷이다.

| 상태 | 언제 | 화면 |
|---|---|---|
| 불러오는 중 | 요청 중 | 뼈대(skeleton). 빙글이만 띄우면 무엇이 올지 모른다 |
| 비어 있음 | 200 인데 0건 | 왜 비었는지 + 다음에 할 일 |
| **못 받음** | 네트워크 · 5xx | **「비어 있음」과 절대 같이 그리지 않는다.** 다시 시도 단추 |
| 권한 없음 | 401 · 403 | 401 은 조용히 갱신 → 실패하면 로그인. 403 은 사유별 |

⚠ **이 구분은 UI 편의가 아니라 안전 문제다.**
안내문 목록을 **못 받았는데** 「안내문이 없습니다」로 그리면, 환자는
**결과가 없다고 믿고 병원에 안 온다.** 병원 안은 전파가 나빠서 실제로
자주 일어난다.

|---|---|
| 토큰 | 만료 시 자동 갱신 · 실패하면 로그인으로. 화면마다 처리하지 말고 한 군데 |

## DB — 요청했던 것은 다 들어갔다  *(v10 · 09-09 확인)*

| 무엇 | 결과 |
|---|---|
| 동의 기록 표 | **v9 신설 · v10 유지.** `consent` — 판·날짜·경로에 더해 `doc_sha256`(그 판 본문의 해시)까지 있다 |
| `notification_type` 에 예약 | **v9 추가 · v10 유지.** `reservation_created` · `reservation_changed` — 요청은 하나였는데 둘로 쪼갰다 |
| `ref_type` 에 `exam_order` | **v9 추가 · v10 유지** |

**둘로 쪼갠 것이 요청보다 낫다.** 「예약이 잡혔다」와 「바뀌었다」는 환자가
할 행동이 다르다.

### v10 에서 더 생긴 것  *(09-09)*

| 무엇 | 화면에 무엇이 달라지나 |
|---|---|
| `lesion.ai_size_*` / `measured_size_*` | 크기가 **AI 원본**과 **판독의 측정값**으로 갈렸다. 화면이 둘을 구분해 보여줄 수 있다 |
| `lesion.is_false_positive` | 판독의가 「이건 병변이 아니다」를 표시한다. **그 단추를 어느 화면에 둘지 정해야 한다** |
| `ai_result.run_status` | `queued · running · done · failed`. 판독이 비동기라 **«분석 중» 화면이 필요하다** |

`is_false_positive` 는 지금 기능으로는 안 쓰이지만, **쌓여야 나중에 서술어를
다시 학습할 수 있다.** 표시할 자리가 없으면 데이터가 한 줄도 안 모인다.

`doc_sha256` 도 요청보다 한 걸음 나간 것이다. 판 번호만 남기면 나중에 약관
파일이 바뀌었을 때 **무엇에 동의했는지 증명이 안 된다.**

### 아직 없는 것 둘 — 둘 다 MVP 밖

| 무엇 | 막히는 화면 |
|---|---|
| 처방 표 2개 | 6. 처방 — **화면 자체가 불가.** 헤더 1행 + 약 여러 줄이라 최소 2개 |
| 문진 이력 | 3. 문진 — 「지난 문진 보기」 불가. `questionnaire` 가 JSONB 한 칸이라 최신 1건만 남는다 |

처방은 「준비 중」 자리만 잡고, **약 이름으로 챗봇에 묻는 경로**는 표 없이도
만들 수 있어 그렇게 이었다.

문진 이력은 **화면에서 그 기능을 약속하지 않는 것**으로 해결한다.
