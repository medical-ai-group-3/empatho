## 1. 라우팅 — 새 경로는 catch-all 위에

`/api/v1/` 아래에 안 걸린 요청을 JSON 봉투로 돌리는 catch-all(`^.*$`)이
`core/api/urls.py` 맨 끝에 있습니다.

```python
urlpatterns = [ path("health", ...), path("tickets", ...) ]
if find_spec("core.urls") is not None:
    urlpatterns.append(path("", include("core.urls")))     # 업무 엔드포인트
urlpatterns.append(re_path(r"^.*$", NotFoundView.as_view()))
```

`cdss_backend/urls.py` 에서 include 를 두 줄로 나누면 위쪽이 전부 잡아먹어서
`/api/v1/patients/` 가 조용히 404 가 됩니다. 응답이 「라우팅이 안 걸렸을 때」와
똑같아서 `router.register` 를 의심하며 헤매게 됩니다. 순서를 한 곳에서만
통제하려고 모았습니다.

### 봉투는 이미 걸려 있습니다 — 아무것도 안 하셔도 됩니다

`settings.DEFAULT_RENDERER_CLASSES` 라 전역입니다. ViewSet 이 `Response(data)` 를
그냥 돌려주면 자동으로 감싸집니다.

```python
return Response({"patient_id": 1})
# → {"success": true, "data": {"patient_id": 1}, "error": null, "trace_id": "..."}
```

페이지네이션 결과(`{count, next, previous, results}`)는 봉투와 나란히가 아니라
**`data` 안에** 들어갑니다.

### 에러는 코드로 던지세요

```python
from core.api.errors import ApiError

raise ApiError("EXAM_PURPOSE_REQUIRED")           # 422 + 문서의 기본 메시지
raise ApiError("SPECIMEN_NOT_BOUND", details={"specimen_id": 801})
```

상태 코드와 메시지가 코드에 붙어 있어 따로 안 적으셔도 됩니다. 카탈로그에 없는
코드를 쓰면 `KeyError` 로 막힙니다 — 오타로 만든 코드가 프론트까지 흘러가지
않게 한 것입니다. 새 코드가 필요하면 `errors.py` 에 먼저 넣고 팀에 알립니다.

DRF 기본 예외(`ValidationError` · `NotFound` · `PermissionDenied` …)도 자동으로
25 개 코드로 옮겨집니다. `serializer.is_valid(raise_exception=True)` 를 쓰시면
`VALIDATION_ERROR` 로 나가고 필드별 사유는 `error.details` 에 담깁니다.

## 3. 권한 — `MatrixPermission` (팀 결정)

```python
from core.api.permissions import MatrixPermission

class PatientViewSet(AuditMixin, viewsets.ModelViewSet):
    resource = "patient"
    permission_classes = [MatrixPermission]
```

**역할 집합이 아니라 리소스 이름 하나만 적습니다.** 누가 무엇을 할 수 있는지는
§15 매트릭스가 답합니다. 메서드가 행위로 옮겨집니다 — `GET`→R · `POST`→C ·
`PUT`/`PATCH`→U · `DELETE`→D.

`patient_pii` 를 따로 만지는 뷰는 `resource = "patient_pii"` 입니다(원무 CRU ·
환자 본인 R). 영상 원본은 `"storage_object"`, 알림은 `"notification"` 입니다.

전체 목록은 `core/api/permissions.py` 의 `MATRIX` 를 보시면 됩니다. 리소스 이름을
안 적거나 매트릭스에 없는 이름을 적으면 `ImproperlyConfigured` 로 막힙니다.

### 단독 권한 3 개는 매트릭스에 없습니다

표 한 칸을 고쳐서 조용히 풀리면 안 되는 것들이라 따로 세워뒀습니다.

```python
from core.api.permissions import CanBindSpecimen, CanDisposeDiscordance, CanUnlockReport

permission_classes = [CanBindSpecimen]      # 검체 바인딩 — 간호 · 유방외과
```

각각 전용 에러 코드가 나갑니다(`BINDING_ROLE_FORBIDDEN` ·
`DISPOSITION_ROLE_ONLY_SURGERY` · `UNLOCK_ROLE_ONLY_SURGERY`).
**검체 바인딩은 간호 · 유방외과 2 부서입니다(09-09 팀 확정).** 인계 문서 §2-7 이
「3 개 부서 공유」로 되어 있는데 그쪽이 갱신될 예정입니다 — 영상의학은 빠집니다.

### `staff.extra_permissions` — 개인별 추가 권한

역할 기본 권한에 사람별로 더합니다. **더하기만 하고 빼지 않습니다.**

```json
{"assessment": ["R"], "report": ["R"]}
```

단독 권한 3 개는 이걸로 안 열립니다. ViewSet 에서 따로 하실 일은 없습니다 —
`MatrixPermission` 이 합쳐서 판정합니다.

## 4. 「본인 것만」 — 두 군데를 다 막아야 합니다

`own_only` 가 걸린 리소스는 한 건과 목록을 따로 막습니다. **권한 클래스는 쿼리셋을
못 봐서 목록을 못 거릅니다.** 한 건만 막고 끝내면 목록에 남의 행이 섞입니다.

```python
from core.api.permissions import MatrixPermission, OwnedOnlyMixin

class MyReportList(OwnedOnlyMixin, generics.ListAPIView):
    resource = "report"
    permission_classes = [MatrixPermission]

    def owned_queryset(self, queryset, account):        # 목록
        return queryset.filter(patient__account=account)

    def is_owned_by(self, obj, account):                # 한 건
        return obj.patient.account_id == account.account_id
```

둘 다 없으면 `ImproperlyConfigured` 로 막습니다 — 소유 판정을 빠뜨린 채 열리는
것보다 낫다고 봤습니다.

**믹스인을 붙여야 하는 리소스**

| 역할 | 리소스 |
|---|---|
| 환자 | `patient` · `reservation` · `report` · `followup` · `consent` · `patient_pii` |
| 전 역할 | `notification` |

`notification` 은 원무든 판독의든 **자기 알림만** 봅니다. 목록 엔드포인트를
만드실 때 빠뜨리기 쉬운 자리입니다.

## 5. 감사 컬럼

### `AuditMixin` — 한 줄이면 채워집니다

방향이 맞습니다. 인증이 붙었으니 `request.user` 가 `Account` 입니다.

```python
def _current_account(self):
    return self.request.user if self.request.user.is_authenticated else None
```

09-08 에 「`created_at`/`updated_at` 은 Django 가, `created_by`/`updated_by` 는 API
계층이」로 정했고, 이 한 줄이 그 나머지 절반입니다. admin 으로 넣은 행은 계속
`NULL` 인 게 정상입니다 — admin 로그인은 `auth_user` 라 `account` 로 이을 수단이
없습니다.

### 아직 안 정해진 것 — `created_by` 를 이름으로도 낼지

명세 §1-1 은 「감사 컬럼 — 전 테이블 공통, **응답에 항상 포함**」이고 그렇게
가기로 했습니다. 다만 `created_by` 가 `account_id` 숫자만 나가면 프론트가 못
씁니다. 이름을 같이 내보낼지(`created_by_name` 같은 걸 붙일지)는 아직입니다 —
`staff.full_name` 을 조인해야 해서 목록 쿼리에 영향이 있습니다.

## 7. `exam_order` 가 예약 신청까지 맡습니다 (09-09 팀 확정 · 0004)

**§5-3 예약 화면이 바뀝니다.** 환자가 날짜·시간만 넣고 신청하는 경로가 생겼습니다.

```
환자가 날짜·시간만 신청  → exam_order(order_status='requested')
                        → notification(reservation_requested) 한 행이 원무에게
원무가 확정             → modality · exam_purpose · ordered_by 를 채우고 'ordered'
                        → notification(reservation_created) 가 환자에게
```

### 바뀐 것

| 컬럼 | 전 | 후 |
|---|---|---|
| `modality` | NOT NULL | **nullable** |
| `exam_purpose` | NOT NULL | **nullable** |
| `patient_id` | nullable | **NOT NULL** |
| `order_status` | ordered · accepted · in_progress · completed · cancelled | **`requested` 추가** |
| `notification_type` | — | **`reservation_requested` 추가** |

```sql
CHECK (order_status = 'requested'
       OR (modality IS NOT NULL AND exam_purpose IS NOT NULL
           AND ordered_by IS NOT NULL))
```

**신청 상태일 때만 세 칸이 비어도 됩니다.** API 가 아니라 DB 로 막습니다 —
Celery 나 admin 으로 들어오는 행은 API 검증을 안 거칩니다.

### 만드실 때 알아두실 것

- **원무 큐는 알림이 아니라 `order_status='requested'` 로 뽑으세요.** 진실은
  `exam_order` 이고 `notification` 은 통지일 뿐입니다. 알림이 안 갔거나 지워져도
  신청은 남아 있어야 합니다.
- **`scheduled_at` 의 뜻이 상태에 따라 다릅니다.** `requested` 면 환자의 희망
  시각, `ordered` 부터는 확정 시각입니다. 원무가 다른 시간으로 확정하면 희망
  시각이 덮여 사라지므로, 확정 알림에 「9월 22일 오전 신청 → 14:00 확정」처럼
  둘을 같이 적어야 합니다. 화면에서 두 값을 다 보여주려면 신청 시각을 어딘가
  들고 있어야 하는데 지금 스키마엔 자리가 없습니다 — 알림 문구에 넣는 방식입니다.
- **`created_by` 와 `ordered_by` 는 다른 값입니다.** 앞은 행을 만든 계정, 뒤는
  검사를 지시한 의료진입니다. 원무가 의사 지시를 대신 입력하면 갈립니다.
- **확정 전 검증은 serializer 에서 하세요.** 세 칸을 비운 채 `ordered` 로 넘기면
  DB 가 `IntegrityError` 를 내고 그건 500 으로 나갑니다. API 단계에서 막아
  `VALIDATION_ERROR`(400)로 돌려주는 게 맞습니다. DB CHECK 은 API 를 안 거치는
  경로를 위한 뒷단입니다.
- 권한은 그대로입니다. 환자의 신청은 `resource = "reservation"`(환자 본인 C),
  원무의 확정은 `resource = "exam_order"`(원무 CRU) 입니다.

## 8. Go 콜백 — `/internal/v1` (명세 21장)

`core/api/internal.py` 하나에 넷이 다 있습니다. **공개 API 와 계약이 다릅니다** —
JWT 가 아니라 서명으로 열고, Go 는 응답 본문을 읽지 않고 상태 코드만 봅니다.

```
POST /internal/v1/storage-objects           I-1  파일 저장 뒤
POST /internal/v1/dicom-instances           I-2  DICOM 헤더 읽은 뒤
POST /internal/v1/notifications/delivery    I-3  알림 보낸 뒤
POST /internal/v1/reports/{id}/narrative    I-4  서술 생성 뒤
```

계약은 `services/gosvc/internal/callback/callback.go` 가 갖고 있습니다. 이미 배포돼
호출 중이라 그쪽이 기준입니다. 서명은 `HMAC-SHA256(secret, ts + "." + body)` 이고
`±5분`을 벗어나면 거절합니다 — Go 가 nonce 를 안 보내서 시간 창이 재전송을 막는
유일한 수단입니다.

**상태 코드가 중요합니다.** Go 는 `4xx` 면 재시도를 포기하고 그 외에는 지수
백오프로 다섯 번 더 두드립니다. 다시 보내도 같은 것만 `4xx` 로 줘야 합니다.

| 상황 | 응답 |
|---|---|
| 서명 불일치 · 시간차 초과 · 비밀값 미설정 | 401 |
| 본문 형식 · 필수 값 없음 | 400 |
| `scope_id` 대상 없음 · 받을 수 없는 `purpose` | 422 |
| DB 오류 | 5xx (재시도가 도움 됨) |
| 성공 · 이미 처리됨 | 200 |

**멱등은 자연키로 잡습니다.** I-1 은 `(bucket, object_key)` 로 `get_or_create`,
나머지 셋은 기존 행 갱신입니다. 멱등 전용 표를 만들지 않았습니다 — 스키마가
18 개로 잠겨 있습니다.

`CALLBACK_SECRET` 은 `conf/gosvc.env` 와 **같은 값**이어야 합니다. 어긋나면
오류가 아니라 401 로 조용히 거절됩니다. 비어 있으면 콜백을 아예 안 받습니다.

### 이 절과 관련해 아직 안 풀린 것

- **`derived_upload` 는 풀렸습니다 (09-10 · 0010).** 파생물은 `storage_object` 가
  아니라 **`image` 행**이 됩니다. `image` 가 `source_object` · `ai_result` ·
  `lesion` 로 「어디서 왔나」를, 자기 `bucket` · `object_key` 로 「바이트가
  어디 있나」를 답합니다. 파생물은 Orthanc 에 안 가고 `empatho-derived` 에만
  있어서 주소가 하나입니다.
- **`prescription_pdf` 는 계속 422 입니다.** 처방 표가 MVP 밖이라 파일이 갈 곳이
  없습니다. 그 티켓으로 올라온 파일은 Garage 에는 있고 DB 에는 없는 고아가
  됩니다.

## 9. 인계 문서와 관련해 팀에 올린 것

다희님 작업에 영향이 있을 수 있어 적어둡니다.

- §15 매트릭스가 v10 을 못 따라간 U 권한 3 건 — `lesion`(영상의학 · 오탐/캘리퍼) ·
  `report`(유방외과 · 대면 설명) · `exam_order`(간호 · 내원 확인). **이미 열어뒀습니다.**
- 검체 바인딩 부서 — 인계 문서 §0 라우트 맵(영상의학+간호)과 §2-7 본문(간호+유방외과)이
  서로 다르고, 유방외과 라우트 목록에는 아예 없습니다. 팀 확정은 간호 · 유방외과입니다.
- `consent` 는 인계 문서에도 화면이 없습니다. 권한(환자 본인 CR)은 근거 없이 저희가
  임시로 정한 상태입니다.
- 인계 문서 §9-10 「선별검사 BI-RADS 0·1·2 제한 CHECK 이 DB 에 없음」 — **DB 로는
  구조적으로 불가능합니다.** 「선별인가」는 `exam_order.exam_purpose` 를 봐야 아는데
  CHECK 은 다른 표를 못 봅니다. API 검증이 정답이고 에러 코드
  `BIRADS3_NOT_ALLOWED_IN_SCREENING` 이 이미 있습니다.
- **`exam_order` 예약 신청 지원(§7)** — v10 문서와 인계 문서 §5-3 을 함께 고쳐야
  합니다. `modality` · `exam_purpose` 가 nullable 이 되고 `patient_id` 가 NOT NULL 이
  되며, `order_status` 에 `requested` · `notification_type` 에 `reservation_requested`
  가 늘었습니다. 팀 확정 NOT NULL 목록도 3 건 → 4 건입니다.
- `exam_purpose` 가 nullable 이 되면서 **설계 원칙 4 「exam_purpose 없으면 오더
  생성 거부」의 뜻이 좁아집니다.** 이제 「확정(ordered 이상) 하려면 필요하다」입니다.
  에러 코드 `EXAM_PURPOSE_REQUIRED` 는 그대로 쓰되 언제 던지는지가 달라집니다.
- **`storage_object` 는 시리즈가 아니라 파일 단위입니다 (09-09 팀 확정 · 0006·0007).**
  v10 문서의 「한 행 = 원본 시리즈 · 파일 1개」를 「원본 파일 1개」로 고쳐야 합니다.
  `series_uid` 의 UNIQUE 를 풀고(색인만) `sop_instance_uid`(nullable · 색인만)를
  신설했습니다. Go 가 파일 하나마다 I-1 을 부르는데 시리즈 1 행이면 MRI 176 장
  중 1 장만 저장되고 나머지가 전부 실패합니다.
  유일성은 **`(bucket, object_key)`** 로 봅니다 — 모든 행에 있고 I-1 시점에
  확정되며 Go 의 멱등키 `obj:<object_key>` 와 같은 자리입니다.
- **`storage_object.report_id` 신설 · 주인이 셋으로 늘었습니다 (0007).**
  `CHECK num_nonnulls(study_id, specimen_id, report_id) = 1` 입니다. 티켓
  `purpose` 가 `dicom_upload`→study · `wsi_upload`→specimen · `report_pdf`→report
  로 갈립니다. **`prescription_pdf` 와 `derived_upload` 는 아직 자리가 없어**
  그 티켓으로 올라온 파일은 한 행도 안 들어갑니다 — 정해지면 넷째 주인을
  더해야 합니다.
- **`storage_object` 주소 제약이 「정확히 하나」에서 「적어도 하나」로 바뀝니다
  (0008).** `CHECK (orthanc_series_id IS NOT NULL OR object_key IS NOT NULL)`.
  **DICOM 은 Orthanc 에, 나머지는 Garage 에 둡니다.** DICOM 도 I-1 때는 Garage 에
  있다가 I-2 로 Orthanc 저장이 확인되면 주소가 그쪽으로 옮겨가고 Garage 키가
  비워집니다 — 사본은 Go 가 지웁니다. XOR 로 조이지 않는 것은 전송이 실패해
  Orthanc ID 가 없으면 Garage 키를 남겨야 해서입니다. 둘 다 비는 행은 여전히
  막습니다.
  (0008 을 낼 당시에는 「양쪽에 두는 것이 정상」으로 알았는데, 09-14 에 Orthanc
  단일 보관으로 정해졌습니다. 제약은 그대로 맞고 근거만 달라졌습니다.)
- **내부 콜백 전용 에러 코드 2 개를 더했습니다** — `TARGET_NOT_FOUND`
  (422) · `UNSUPPORTED_PURPOSE`(422). 명세 §1-4 의 25 개는 **공개 API
  의 계약이라 건드리지 않았습니다.** 내부 콜백은 계약이 달라 `INFRA_ERRORS`
  쪽에 있습니다.
- **`patient.primary_staff_id` 신설 — 주치의 (0009).** `FK staff · nullable ·
  PROTECT`. 간호과가 환자를 배정할 때 지정합니다. 환자 앱 예약 내역 · 결과지의
  「담당 주치의」, 영상의학 · 간호 화면의 담당의 표시, 유방외과의 「내 환자 목록」
  필터가 이 칸으로 돕니다. **알림은 걸지 않습니다** — `notification_type` 추가
  없습니다. 권한은 §15 첫 행이 이미 간호에게 `patient` `RU` 를 줘서 새로 정할

- **`account.account_status` 신설 · `is_active` 기본값이 False 로 (09-15 · 0012).**
  가입 승인과 로그인 가능 여부를 나눴습니다. v10 문서에 `account_status` 행을
  더하고 `is_active` 기본값을 고쳐야 합니다.
- **`ai_result` 의 주인이 study XOR specimen 이 됩니다 (0012).**
  `study_id` 가 nullable 이 되고 `specimen_id` 가 생기며
  `CHECK num_nonnulls(study_id, specimen_id) = 1` 이 붙습니다. **병리 AI 결과가
  지금까지 저장 자체가 안 되던 것**을 고친 것입니다.
- **`study.read_status` · `assessment.read_stage` 값이 바뀝니다 (0012).**
  1차 판독 게이트가 팀 결정으로 없어져 `first_locked` · `ai_revealed` · `first`

- **`lesion.modality` CHECK 이 v10 에서 빠져 있었습니다 (0012 에서 채움).**
  `choices` 만 있고 `Meta.constraints` 가 비어 DB 가 아무 문자열이나 받았습니다.
- **`exam_order.cancel_reason` · `cancelled_by` 신설 (0012).** 영상의학과 협진
  거절용입니다. 「누가 물렸나」를 `notification.staff_id` 로 가르던 09-09 결정은
  거절 주체가 둘이 되면서 깨졌습니다 — `cancelled_by` 가 대신합니다.
- **컬럼 6 개가 화면 명세에서 더 들어왔습니다 (0012).**
  `exam_order.assigned_to` · `order_note` · `specimen.assigned_to` ·
  `clinical_note` · `amend_history` · `patient.first_visited_at` ·
  `report.last_viewed_by`. `report.view_count` 는 기본 0 · NOT NULL 이 됐습니다.
- **명세 문서 오류 셋** — `patient_pii` 복합 UNIQUE 는 넣지 않습니다(phone 단독이
  이미 더 엄격), `patient.last_study_at` 은 없는 컬럼이며, `followup` 은
  `call_at`/`assigned_to` 가 아니라 `called_at`/`called_by` 입니다.
- **파생물은 `image` 행이 됩니다 (09-10 · 0010).** `image.object_key` 단독
  UNIQUE 를 풀고 **`(bucket, object_key)`** 로 바꿨습니다 — 그래야
  `empatho-original` 과 `empatho-derived` 에 같은 키를 쓸 수 있고, 이 쌍이
  메시 스텁의 조인 키가 됩니다(§11). v10 문서의 `image` 절을 고쳐야 합니다.
- **`exam_order.questionnaire`(jsonb) 신설 (0010).** 문진의 진실이 이쪽으로
  옮겨갑니다 — `patient.questionnaire` 는 최신 1건 캐시입니다(§10). v10 문서에

- **`image.kind` 의 `mesh` 가 셋으로 갈립니다 (09-10 MRI 담당 확인 · 0011).**
  `mesh_breast` · `mesh_dense` · `mesh_lesion`. CHECK 도 같이 바뀝니다.
  v10 문서의 `IMAGE_KIND` 목록을 고쳐야 합니다.
- **`ai_result.requested_socket_id` 신설 (0011).** 소켓이 4→5 · 2→1 로 재배치되어
  요청 번호와 실제 번호가 갈립니다. 실제는 `model` FK 가 답하므로 요청 쪽만
  새로 뒀습니다(§11).
- **MRI 응답의 3D 메시는 `ai_result.result` 에 넣지 않습니다.** 24~33MB 중

- **`exam_order.order_status` 의 `cancelled` 가 거절을 겸합니다.** `rejected` 를
  따로 두지 않고, 누가 물렸는지는 `notification.staff_id` 로 갈립니다 — 거절이면

  과는 다른 건입니다.

## 10. 문진 — 표가 아니라 버전 붙인 yaml (09-10 · 0010)

문항을 표로 두지 않았습니다. `core/questionnaire/v1.yaml` 에 정의를 두고
답변만 jsonb 로 저장합니다. 선택지 id 가 고정이라 과거 답변의 뜻이 안 바뀝니다.

```python
from core.api import questionnaire

order.questionnaire = questionnaire.validate(request.data["questionnaire"])
# → {"form_version": "v1", "answers": {"has_symptom": "yes"}}
```

- **`form_version` 은 서버가 찍습니다.** 앱이 보낸 값이 있어도 무시합니다 —
  옛 앱이 새 문항에 옛 판을 붙이는 것을 막을 방법이 그것뿐입니다.
- **덜 채워도 통과합니다.** 간호가 나중에 보완하는 경로(§3.12)가 있습니다.
- 모르는 문항 · 모르는 선택지는 `VALIDATION_ERROR` 입니다.
- 화면에 뿌릴 문항은 `questionnaire.active_questions()` 로 가져오세요.

**진실은 `exam_order.questionnaire` 입니다.** 문진은 방문 때 받는 것이라 방문마다
한 벌이고, 그래야 이력이 남습니다. `patient.questionnaire` 는 조회 편의를 위한
**최신 1건 캐시**입니다. 앱은 한 벌로 보내고 서버가 한 트랜잭션에서 양쪽에
담으세요 — 화면이 나눠 보내면 한쪽만 저장되는 경우가 생깁니다.

⚠ `v1.yaml` 은 아직 **뼈대**입니다. v9 예시 문항 4 개만 들어 있고 간호과 확인
전입니다. 실제 문항이 오면 `v2.yaml` 을 새로 만듭니다 — v1 은 지우지 않습니다.

## 11. AI 추론 결과 — Celery 가 지킬 것 (09-10 추론 서버 인계 문서 · 0011)

Celery 는 수용님이 맡으시는데, DB 에 걸리는 제약이라 여기 적습니다.

### MRI 메시는 `ai_result.result` 에 넣지 않습니다

MRI 응답이 24~33MB 인데 **99.98% 가 3D 메시**입니다 — 정점·삼각형 좌표가 한
응답에 280만 개 들어 있습니다. 메시를 빼면 4.3KB 고 나머지 모달리티는 전부
7KB 미만입니다.

`core/mesh.py` 가 걷어냅니다.

```python
from core import mesh

stripped, parts = mesh.split(응답, study_id)
ai_result.result = stripped          # 24MB 가 아니라 4.3KB
```

메시가 있던 자리에는 **키를 지우지 않고 스텁**을 넣습니다.

```jsonc
"density": { "breast_mesh": { "$mesh_ref": {
    "bucket": "empatho-derived", "object_key": "study/201/mesh/breast_mesh.json",
    "content_type": "application/json", "byte_size": 12300000,
    "vertex_count": 1400000 }}}
```

- 스텁이 **`image_id` 가 아니라 `(bucket, object_key)` 를 듭니다.** `image` 행은
  업로드 뒤에야 생기는데 주소는 지금 정할 수 있어서, JSON 을 두 번 쓰지
  않아도 됩니다. `image` 에 `(bucket, object_key)` UNIQUE 가 걸려 있어(0010)
  그 쌍이 곧 조인 키입니다. 스텁인지 보려면 `mesh.is_ref(값)` 을 쓰세요.
- **메시 말고는 아무것도 걷어내지 않습니다.** 지금 리포트가 안 쓰는 필드도
  나중에 필요하고 빠지면 조용히 망가집니다. 그래서 경로를 명시하고 추측하지
  않습니다 — `_mesh` 로 끝나는 키를 훑으면 언젠가 메시가 아닌 것을 지웁니다.
- 걷어낸 뒤에도 **1MB 를 넘으면 저장하지 않고 터집니다.** 추론이 메시 필드를
  하나 더 늘리면 30MB 행이 조용히 들어가는 대신 여기서 걸립니다.

메시는 `.json` 으로 올립니다. 추론팀의 glTF/Draco 계획은 확인 중입니다.

### 파생물 kind — 메시가 셋입니다 (0011)

| kind | 언제 | 필수 FK |
|---|---|---|
| `overlay` | 맘모 영상당 1 | source_object · ai_result |
| `thumbnail` | 영상당 1 | source_object |
| `mesh_breast` | MRI 검사당 1 | source_object · ai_result |
| `mesh_dense` | MRI 검사당 1 | source_object · ai_result |
| `mesh_lesion` | MRI **병변당 1** | source_object · ai_result · **lesion** |

한 덩이 `mesh` 를 셋으로 나눈 이유 — 앞의 둘은 `lesion` 이 null 이고 뒤는
필수인데, 한 kind 로 두면 그 차이를 DB 가 못 걸고 `lesion` 이 null 인 두 행이
구분도 안 됩니다. kind 를 고르는 쪽이 Celery 라 추론도 Go 도 안 바뀝니다.

`mask` · `heatmap` 은 **아무도 내지 않습니다** — 초음파는 폴리곤 JSON, 병리
응답에 마스크가 없고, 맘모는 분할을 하지 않습니다. 계속 422 로 거절합니다.

### 순서

```
① stripped, parts = mesh.split(응답, study_id)
② AiResult 저장 (result=stripped)
③ Lesion 행 생성 → parts 의 lesion_index 를 lesion_id 로 해석
④ part 마다 tickets.issue("derived_upload", "study", study_id, derived={...})
⑤ Go 업로드 → I-1 → image 행
```

②가 ⑤보다 먼저인데도 괜찮은 이유가 위의 `(bucket, object_key)` 입니다.
`part.object_key` 는 이미 `object_key_prefix("study", study_id)` 아래라 티켓이
열어주는 자리와 같습니다.

### 소켓 번호가 4→5 · 2→1 로 넘어갑니다 (0011)

**`ai_result.requested_socket_id` 를 새로 뒀습니다.** 응답의
`requested_socket_id` 를 그대로 넣으세요. **실제 처리한 소켓은 `model` FK →
`ai_model.socket_id`** 입니다. 둘이 다르면 그 차이 자체가 재배치 기록입니다 —
하나만 저장하면 흔적이 사라집니다.

### 상태 기록

- **`abstained: true` 를 `run_status='failed'` 로 기록하지 마세요.**
  `run_status='done'` + `abstained=true` + `abstain_reason` 입니다.
  **abstained 를 failed 로 쓰면 재시도 대상이 잘못 잡힙니다.**
- **`grade.malignancy` 는 `lesion.malignancy_p` 에 저장만 합니다.**
  화면과 소견문에는 내지 않습니다.
- 시간 상한 — 맘모 33.5초 · 첫 MRI 175초. `elapsed_sec` 는 `Decimal(8,3)` 이라
  여유가 있습니다.

## 12. 화면 명세 여섯 부서분 반영 (09-15 · 0012)

영상의학과 · 병리과 · 유방외과 · 원무과 · 간호과 · 관리자 화면 명세의
「백엔드에서 바꿔야 할 것」을 모아 한 번에 넣었습니다. 적용 시점에 12개 표가
전부 0행이라 NOT NULL 전환과 CHECK 교체를 백필 없이 했습니다.

### 가입 승인과 로그인을 나눴습니다

```python
account.account_status   pending · active · rejected · suspended   기본 'pending'
account.is_active        로그인 가능 여부                            기본 False
```

**인증(`core/api/auth.py`)은 `is_active` 만 봅니다.** 승인 흐름을 거기 섞으면
상태가 늘 때마다 인증 코드를 고쳐야 합니다. 대신 **가입 엔드포인트가 둘을 다
정해야 합니다.**

| | `account_status` | `is_active` |
|---|---|---|
| 직원 가입 | `'pending'` | **`False`** |
| 환자 가입 | `'active'` | `True` |
| 관리자 승인 | `'active'` | `True` |
| 관리자 거절 | `'rejected'` | `False` |
| 관리자 정지 | `'suspended'` | `False` |

`is_active` 기본값을 `False` 로 둔 것은 **빠뜨렸을 때 닫히는 쪽이 맞아서**입니다.
환자 가입에서 `is_active=True` 를 안 넣으면 그 환자가 로그인을 못 합니다 —
열려 있는 것보다 낫다고 봤습니다.

`account_status` 는 NOT NULL 입니다. 환자도 값이 있어야 하므로 가입할 때
`'active'` 를 명시하세요. 안 넣으면 `'pending'` 이 되어 관리자 승인 큐에 쌓입니다.

### AI 결과의 주인이 검사 아니면 검체입니다

```sql
CHECK (num_nonnulls(study_id, specimen_id) = 1)
```

**병리 AI 결과는 지금까지 저장이 아예 안 됐습니다** — `ai_result.study_id` 가
NOT NULL 인데 검체에는 study 가 없습니다. `storage_object_owner_ck` 와 같은
모양으로 풀었습니다.

- 크롭 여러 장이면 장마다 한 행이고 `specimen_id` 가 묶습니다
- `patient_id` 는 계속 NOT NULL 입니다 — 병리든 영상이든 환자는 항상 있습니다
- `GET /ai-results?study={id}` 와 `?specimen={id}` 가 둘 다 필요합니다

### 1차 판독 게이트가 없어졌습니다

```
study.read_status      pending · draft · finalized     (first_locked · ai_revealed 삭제)
assessment.read_stage  draft · final                   (first 삭제) · 기본 'draft'
```

팀 결정으로 「1차 판독을 먼저 잠그고 그다음 AI 를 공개」하는 순서를 없앴습니다.
**`PATCH /studies/{id}/reveal-ai` 는 만들지 마세요** — 게이트가 없습니다.
AI 를 볼지 말지는 판독의가 접는 패널로 정합니다.

에러 코드 `AI_LOCKED_BEFORE_FIRST_READ` 는 카탈로그에 남아 있지만 던질 자리가
없어졌습니다. 명세 25개는 공개 계약이라 지우지 않았습니다.

### 선착순 집기 — 비어 있는 것이 큐의 조건입니다

```
exam_order.assigned_to    영상의학과 대기 큐
specimen.assigned_to      병리과 접수 대기 큐
```

```python
ExamOrder.objects.filter(order_status="ordered", assigned_to__isnull=True)
```

동시 집기는 **조건부 UPDATE** 로 막습니다. 0행이면 `ALREADY_ASSIGNED`(409) 입니다.

```python
updated = (ExamOrder.objects
           .filter(pk=pk, assigned_to__isnull=True)
           .update(assigned_to=staff, order_status="accepted"))
if not updated:
    raise ApiError("ALREADY_ASSIGNED")
```

`select_for_update` 로 잡고 확인하는 방식보다 이쪽이 짧고, 락을 안 잡습니다.
유방외과는 `assigned_to` 가 없습니다 — `patient.primary_staff_id` 로 이미
갈려 있어 「내 환자」가 곧 큐입니다.

### 협진 거절 — 사유가 DB 로 강제됩니다

```sql
CHECK (cancelled_by IS NULL OR cancel_reason IS NOT NULL)
CHECK (cancel_reason IS NULL OR order_status = 'cancelled')
```

영상의학과가 `PATCH /exam-orders/{id}/reject` 로 돌려보내면 `cancelled` 로 가고
사유가 남습니다. **의료진이 물리면 사유 없이는 행이 안 들어갑니다.**

`rejected` 를 따로 두지 않는 것은 그대로입니다. 다만 「누가 물렸나」를
`notification.staff_id` 로 가르던 방식은 **거절 주체가 원무 · 영상의학 둘이
되면서 깨졌습니다.** 이제 `cancelled_by` 가 답하고, 역할은
`cancelled_by.account.role` 로 나옵니다. `cancelled_by` 가 null 이면 환자 취소입니다.

### 그 밖의 컬럼

| 컬럼 | 쓰는 화면 |
|---|---|
| `exam_order.order_note` | 유방외과 촬영 요청 의견서. 촬영부위는 받지 않습니다 |
| `patient.first_visited_at` | 원무 초진/재진. `created_at` 으로는 어긋납니다 — 앱을 먼저 가입하고 나중에 옵니다 |
| `report.last_viewed_by` | 유방외과 열람. 「확인」이 아니라 「열람」입니다 — 자동 기록입니다 |
| `report.view_count` | **기본 0 · NOT NULL** 로 바꿨습니다. nullable 이면 `F("view_count") + 1` 이 NULL 에 더해져 계속 NULL 입니다 |
| `specimen.clinical_note` | 유방외과 의뢰 문구 |
| `specimen.amend_history` | 병리 판독 정정 이력 (아래) |

### 병리 정정은 새 행이 아니라 배열입니다

영상의학은 새 `assessment` 행을 만들고 옛 행이 `superseded_by` 로 가리킵니다.
**검체는 그 방식을 쓸 수 없습니다** — `specimen_label` 이 UK 라 행을 늘릴 수 없고,
`discordance_flag.specimen_id` 가 옛 행을 가리킨 채 남습니다.

```python
specimen.amend_history = (specimen.amend_history or []) + [{
    "diagnosis": specimen.diagnosis, "b_category": specimen.b_category,
    "finding_note": specimen.finding_note, "reported_by": specimen.reported_by_id,
    "finalized_at": ..., "amend_reason": ..., "amended_at": ...}]
```

옛 값을 배열에 밀어넣고 본 컬럼을 덮어씁니다. 대조 링크가 안 깨지고 표도 안 늡니다.

### `lesion.modality` CHECK 이 v10 에서 빠져 있었습니다

`choices` 만 있고 `Meta.constraints` 가 비어 있어 **DB 는 아무 문자열이나
받았습니다.** 다른 표는 전부 걸려 있어 누락이 맞습니다. 이번에 채웠습니다 —
`mammo · us · mri` 또는 NULL. **`pathology` 는 없습니다** — 검체가 병변에 붙지
병변이 병리에서 나지 않습니다.

### 파생물 `mask` 를 열었습니다

```python
"mask": ("source_object_id", "ai_result_id"),
```

병리 조직 분할 결과입니다. 크롭 한 장당 PNG 한 장이고 `image.kind='mask'` 로
들어갑니다. `heatmap` 은 계속 422 입니다 — 아무도 내지 않습니다.

병리 서빙이 `return_tissue_mask=True` 로 켜기 전까지는 열어둬도 올라올 것이
없습니다 (담당 별도).

### 에러 코드

`ALREADY_ASSIGNED`(409)를 **`INFRA_ERRORS`** 에 더했습니다. 명세 §1-4 의 25개는
공개 API 계약이라 건드리지 않았습니다.

`ALREADY_CONFIRMED` 는 `main` 에서 이미 `SPEC_ERRORS` → `INFRA_ERRORS` 로
옮겨졌습니다 (`16568c6`). 두 코드가 같은 자리에 있습니다.

### 명세 문서 쪽 오류 셋

라이브와 대조하다 나온 것입니다. 문서가 고쳐집니다.

- `patient_pii` 복합 UNIQUE — **넣지 않습니다.** `phone` 단독 UNIQUE 가 이미
  있고 그쪽이 더 엄격합니다. 복합으로 바꾸면 세 칸이 전부 nullable 이라
  전화번호 없는 환자 둘이 통과합니다. 중복 검사는 `POST /patients` 가 세 값으로
  조회해서 합니다.
- `patient.last_study_at` — 없는 컬럼입니다. `GET /patients/{id}/timeline` 로
  가기로 해서 추가하지 않습니다.
- `followup` 컬럼명 — `call_at` 이 아니라 **`called_at`** 이고, `assigned_to` 는
  없습니다. 「누가 연락했나」는 **`called_by`** 가 담습니다.
